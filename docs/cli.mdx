# CLI reference

`sheppy` with a manifest path (or nothing) opens [the TUI](../tui). If the
manifest is missing, unreadable, isn't valid YAML, or isn't a YAML mapping, it prints the error and exits 1
instead. With a **verb**, it runs headless — the verbs never import Textual, so they work over
SSH on a machine with no display.

```bash
sheppy [MANIFEST]          # open the TUI (MANIFEST defaults to ./sheppy-manifest.yaml)
sheppy <verb> [...]        # headless: up, status, logs, restart, down, daemon
sheppy --version           # or -V
sheppy --help              # or -h; sheppyd --help works too
```

## Verbs

### `sheppy up <profile> [--manifest PATH]`

Bring the system to a [profile](../profiles). `<profile>` is a name:
`sheppy up mock` reads `profiles/mock.yaml` next to the manifest.
`--manifest` defaults to `./sheppy-manifest.yaml`.

It prints a plan (`start`, `restart`, or `stop` per node). Each `restart`
line says in parentheses what changed: `alternative <old> → <new>`, or
`launch command changed`. When the params differ too, they follow after
`params`, each with the running value, then the new one (`—` for a param set
on only one side).

```
$ sheppy up fast
restart camera (launch command changed; params fps: 15 → 30; frame_id: "camera" → "cam_front")
restart lidar (alternative velodyne_lo → velodyne_hi)
start planner
```

Then it:

- starts selected nodes that aren't running, and restarts ones running a
  different alternative or command (params are part of the command);
- stops nodes in the manifest that the profile doesn't select;
- leaves running nodes whose names aren't in the manifest alone (it matches
  by name, so a node with the same name from another manifest is treated as
  this manifest's own);
- leaves a selected node as it is, running or not, when its launcher fails
  to resolve (a missing compose file, say): it prints the failure and exits
  1 after converging the rest.
- never launches a selected alternative that has manifest errors (an
  `executable` alternative missing `executable`, say), or whose node has
  them (a node `name` with a space, say): it prints the errors
  as `<node>: not launched, ...`, leaves that node as it is, and exits 1
  after converging the rest.

All the starts go out at once, with no ordering between nodes. It then prints
`waiting for N node(s) to settle`, waits for every node to leave `launching`,
and prints each node's final state, with the last line of a crashed
node's log indented under it. The wait is bounded by the daemon's grace
periods: `launch_grace + stop_grace + kill_grace + 10` seconds from
[`sheppyd.json`](../guides/sheppyd#configuration), 22 seconds with the
defaults. A [launcher plugin](../guides/launcher-plugins) that sets its own
`grace["launch"]` on a detached descriptor raises the bound by the same
amount. Running it twice in a row prints `already converged` the second
time.

`up` is the only verb that starts `sheppyd` when it isn't running, and the
daemon keeps this terminal's environment — see
[ROS integration](../ros-integration#where-your-nodes-get-their-environment).

**Exit code:** 1 if the manifest or profile can't be loaded, if `sheppyd`
can't start, if a selected node's launcher fails to resolve, if a selected
alternative has manifest errors, if `sheppyd` rejects a launch (it prints the
daemon's error, for example a command that doesn't exist), if any selected
node isn't `running` once things settle (`crashed`, or `stopped` because it
never started), or if they don't settle within the bound above.
Recoverable problems, such as a profile selection the manifest no longer has
or a manifest error in an alternative that isn't selected, print as
`warning:` on stderr and don't stop the launch.

### `sheppy status [<node>]`

One line per node `sheppyd` supervises: name, state, alternative, pid, and
uptime or exit code.

```
$ sheppy status
clock                running    ticker         pid=3948253 up 22s
worker               crashed    flaky          pid=3948421 exit=1
```

It exits 0 even when a node has crashed, so read the output rather than the
exit code. It prints `(nothing supervised)` for an empty table and
`sheppyd: not running` when there's no daemon.

With a node name it prints that node's line, then the alternative, params,
and start command the node was launched with. These are the values
`sheppy restart` reruns, which can differ from the profile if you have
edited it since.

```
$ sheppy status camera
camera               running    realsense      pid=3948253 up 22s
  alternative  realsense
  params       enable_depth: false
               fps: 30
  start        ros2 launch realsense2_camera rs_launch.py --ros-args ...
```

Exits 1 if `sheppyd` doesn't supervise that node or isn't running.

### `sheppy logs <node> [-n N | --all] [-f]`

Print the last `N` (default 50, must be at least 1) lines of a node's output. `sheppyd` keeps the
last 300 lines in memory; the full per-run log files are under
`~/.sheppy/logs/<node>/`. Exits 1 if the node is unknown or the daemon isn't
running.

With `--all`, print the node's latest run file from the start instead. It reads
the file from disk (the `log_dir` set in `sheppyd.json`, `~/.sheppy/logs/` by
default), so it works without `sheppyd` running and for a node it no longer
supervises, such as one you stopped. `sheppyd` keeps the last `keep_runs`
(default 5) runs per node.
`--all` and `-n` can't be used together. Exits 1 if the node has no run files.

With `-f` (`--follow`), keep printing the node's output as it is written,
until Ctrl-C. `-f` also reads the run files from disk: it prints the last `N`
lines of the latest run (with `--all`, the whole run), then follows that file.
When the node restarts, it moves to the new run file and prints
`-- new run: <file>` on stderr. If the node has no run files yet, it waits for
the first one, so `sheppy logs camera -f` works before `sheppy up`.

### `sheppy restart <node>`

Restart a node, including a crashed one, with the alternative, params, and
command it was launched with, then print the alternative and params. `restart`
doesn't pick up manifest or profile edits; use `sheppy up` for that.

For a node `sheppy up` launched, `restart` also checks the manifest and
profile `up` used, and prints a warning with the `sheppy up` command to run
if they now give a different alternative, command, or params. Nodes launched
from the TUI aren't checked. If `sheppyd` isn't running but left nodes
running when it stopped, `restart` starts it first, and the new daemon
re-adopts them. Exits 1 if the node is unknown or the daemon isn't running
and can't be started. `sheppy woof`, its old name, still works.

### `sheppy down`

Stop every node `sheppyd` supervises, from any manifest, printing
`stopped <node>` for each, then stop the daemon itself. If the daemon isn't
running but left nodes running when it stopped (after `sheppy daemon stop`),
`down` starts it, the new daemon re-adopts those nodes, and `down` stops them;
it exits 1 if the daemon can't start. With no daemon and no nodes left
running, it prints `sheppyd: not running` and exits 0.

There's no headless verb to stop or start a single node. Use `x` and `space`
in the TUI, or `sheppy up` a profile that doesn't select that node.

### `sheppy daemon status` / `sheppy daemon stop`

`status` reports whether `sheppyd` is running and how many nodes it
supervises. `stop` stops the daemon **and leaves the nodes running**; the next
launch starts a new daemon, which
[re-adopts them](../guides/sheppyd#survivability-and-re-adoption). That is the
difference from `sheppy down`, which stops the nodes too.

## Recipes

Bring up a profile and look at it:

```bash
sheppy up mock; sheppy status
```

Find out why a node crashed, then try again:

```bash
sheppy status                  # which node, and its exit code
sheppy logs camera -n 200      # its last output
sheppy logs camera --all       # or its whole latest run
sheppy logs camera -f          # or watch it live, across restarts
sheppy restart camera
```

Apply a manifest edit to a running system:

```bash
sheppy up mock                 # restarts only the nodes whose command changed
```

Start over with a different shell environment:

```bash
sheppy down
source /home/me/ws/install/setup.bash
sheppy up mock
```

## Exit codes at a glance

| Situation | Code |
|-----------|------|
| Success | 0 |
| TUI: manifest missing, unreadable, not valid YAML, or not a mapping | 1 |
| Daemon not running — `status`, `daemon`, and `down` with no nodes left running | 0 |
| Daemon not running — `logs`, `status <node>`, and `restart` with no nodes left running | 1 |
| `down`, `restart`: the daemon left nodes running and couldn't be started again | 1 |
| Unknown node (`logs` without `-f`, `restart`, `status <node>`) | 1 |
| `logs --all`: the node has no run files | 1 |
| `logs -f`: a node name that can't be a manifest node (such as a path) | 1 |
| `up`: manifest/profile failed to load, `sheppyd` couldn't start, a launcher failed to resolve, a selected alternative has manifest errors, `sheppyd` rejected a launch, a selected node isn't running once settled, or settle timeout | 1 |
| `sheppyd` died mid-command (`sheppy: sheppyd: sheppyd connection lost`) | 1 |
| Usage error: a missing or unexpected argument, an invalid `-n` (not a positive integer), `-n` together with `--all`, or an unknown `daemon` action (argparse prints the usage) | 2 |
| Interrupted with Ctrl-C, including stopping `logs -f` | 130 |

## `sheppyd`

You normally never run the daemon yourself — the first launch action spawns
it. Running `sheppyd` by hand starts it in the foreground: it takes the
single-instance lock, re-adopts surviving children, and serves on the local
socket until SIGTERM/SIGINT. See the
[sheppyd guide](../guides/sheppyd) for its lifecycle, configuration, and
protocol.

## Environment

| Variable | Effect |
|----------|--------|
| `SHEPPY_HOME` | Pin logs, state, config, and the socket under this directory instead of `~/.sheppy` (see [what's in it](../guides/sheppyd#home-directory)). Useful for test isolation. Keep it short: the socket path must fit in 107 bytes, or `sheppyd` won't start. |
| `NO_COLOR` | Set to any non-empty value to turn off the colors in the headless verbs' output. They're already off when output goes to a pipe or file. |
| `COLORTERM=truecolor` | Required for the TUI's full palette over SSH — see [colors washed out over SSH?](../tui#colors-washed-out-over-ssh) |
