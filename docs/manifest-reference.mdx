# Manifest reference

Field-by-field lookup for `sheppy-manifest.yaml`. If you want to learn
manifest authoring by example, start with [The manifest](../manifest) instead
— this page is the companion you come back to once you know what you're
looking for.

## Top level

| Field | Required | Type | Meaning |
|---|---|---|---|
| `machines` | no | list of [machine](#machines) | Declares the machines an alternative can reference. Omit entirely to run everything locally. |
| `nodes` | no* | list of [node](#nodes) | The logical units of your system. *Not enforced by the loader, but a manifest with no nodes has nothing to launch. |

## Machines

```yaml
machines:
  - name: robot
    host: 10.0.0.20
    user: researcher
    ros_setup: /opt/ros/humble/setup.bash
```

| Field | Required | Type | Meaning |
|---|---|---|---|
| `name` | **yes** | string | Referenced by an alternative's `machine:`. Must be unique; the loader errors if empty or missing. |
| `host` | **yes** | string | Stored on the machine record. The loader errors if empty or missing. |
| `user` | **yes** | string | Stored on the machine record. The loader errors if empty or missing — this one surprises people, see [below](#things-that-surprise-people). |
| `ros_setup` | no | string | A path `source`d before the command of any alternative whose `machine:` names this machine. |

## Nodes

```yaml
nodes:
  - name: camera
    description: "RGB-D source"
    select: single
    alternatives: [...]
```

| Field | Required | Type | Meaning |
|---|---|---|---|
| `name` | **yes** | string | Must be unique across the manifest; the loader errors on a duplicate. |
| `description` | no | string | Stored, but rendered nowhere in the TUI today. |
| `select` | no | string | Defaults to `single`, the only accepted value — see [below](#things-that-surprise-people). |
| `alternatives` | **yes** | non-empty list of [alternative](#alternatives) | The interchangeable ways to do this job. |

## Alternatives

Common fields, valid regardless of `kind`:

| Field | Required | Type | Meaning |
|---|---|---|---|
| `id` | **yes** | string | Unique within its node; the loader errors on a duplicate. |
| `kind` | **yes** | string | Must name a registered launcher — one of `executable`, `launch_file`, `process`, `docker`, or a kind added by a third-party plugin. |
| `machine` | no | string | Must name a declared machine (validated). Selects that machine's `ros_setup` to source before the command, and is shown in the TUI's host column and detail panel. It does **not** launch the command remotely — see [below](#things-that-surprise-people). |
| `params` | no | mapping | How it's used depends on `kind` — see the per-kind sections below. |
| `publishes` | no | list of string | Documentation only — see [below](#things-that-surprise-people). |
| `subscribes` | no | list of string | Documentation only — see [below](#things-that-surprise-people). |

Everything else in an alternative's mapping is kind-specific — `package`,
`executable`, `launch_file`, `command`, `container`, `compose` — documented
per kind below.

## Kinds

Every kind, builtin or plugin, registers through the same `sheppy.launchers`
entry-point group in `pyproject.toml`. `executable`, `launch_file`, and
`process` ship in sheppy's core; **`docker` ships as a separate plugin
module** (`sheppy.launch.docker`) using that same mechanism. A third party
adds a new kind exactly the same way — see
[Writing a launcher plugin](../guides/launcher-plugins).

| Kind | Source | Requires | Optional fields |
|---|---|---|---|
| [`executable`](#executable-core) | core | `package`, `executable` | `params`, `machine`, `publishes`, `subscribes` |
| [`launch_file`](#launch_file-core) | core | `package`, `launch_file` | `params`, `machine`, `publishes`, `subscribes` |
| [`process`](#process-core) | core | `command` | `machine`, `publishes`, `subscribes` (`params` accepted but ignored) |
| [`docker`](#docker-plugin) | plugin (`sheppy.launch.docker`) | exactly one of `compose` or `container` | `params`, `ros_node_name`, `machine`, `publishes`, `subscribes` |

### `executable` (core)

Runs `ros2 run <package> <executable>`.

| Field | Required | Meaning |
|---|---|---|
| `package` | **yes** | ROS package name. |
| `executable` | **yes** | Executable name within the package. |
| `params` | no | Appended as `--ros-args -p key:=value` for each entry. |

### `launch_file` (core)

Runs `ros2 launch <package> <launch_file>`.

| Field | Required | Meaning |
|---|---|---|
| `package` | **yes** | ROS package name. |
| `launch_file` | **yes** | Launch file name within the package. |
| `params` | no | Appended as `key:=value` for each entry, ROS launch-argument style. |

### `process` (core)

Runs `command` as-is, with no ROS wrapping — for anything that isn't a ROS
process, like a simulator GUI.

| Field | Required | Meaning |
|---|---|---|
| `command` | **yes** | The shell command to run, verbatim. |
| `params` | no | **Ignored.** sheppy emits a warning if you set it. |

### `docker` (plugin)

Runs a container, supervised like any other process. Provided by the
`sheppy.launch.docker` plugin, registered under the `docker` kind. Requires
exactly one of:

| Field | Required | Meaning |
|---|---|---|
| `container` | one of `container`/`compose` | An inline container definition (e.g. `image`, `network_mode`, `command`). |
| `compose` | one of `container`/`compose` | A reference to an existing compose file: needs `file` and `service`. |
| `params` | no | If non-empty, always written to a params file that's mounted read-only into the container and passed via `--ros-args --params-file`. |
| `ros_node_name` | no | Scopes the written params file to that node name; without it the params apply under the ROS wildcard `/**`. |

#### Which compose keys sheppy translates

The same table applies to an inline `container` and to a service read from a
`compose` file. sheppy borrows compose's vocabulary and turns each key into a
`docker run` flag; it does not run compose.

| Compose key | Becomes |
|---|---|
| `image`, `command`, `entrypoint` | The image and its argv. |
| `environment`, `env_file` | `-e`, `--env-file` |
| `volumes`, `tmpfs`, `volumes_from`, `read_only` | `-v` (short and long form), `--tmpfs`, `--volumes-from`, `--read-only` |
| `devices`, `device_cgroup_rules`, `gpus` | `--device`, `--device-cgroup-rule`, `--gpus` (short form only, e.g. `gpus: all`) |
| `network_mode`, `ipc`, `pid`, `uts`, `userns_mode`, `cgroup`, `cgroupns_mode` | `--network`, `--ipc`, `--pid`, `--uts`, `--userns`, `--cgroupns`, `--cgroupns` |
| `ports`, `expose` | `-p` (short `host:container` form only), `--expose` |
| `hostname`, `domainname`, `mac_address`, `extra_hosts`, `dns`, `dns_search`, `dns_opt` | `--hostname`, `--domainname`, `--mac-address`, `--add-host`, `--dns`, `--dns-search`, `--dns-option` |
| `privileged`, `cap_add`, `cap_drop`, `security_opt`, `user`, `group_add` | `--privileged`, `--cap-add`, `--cap-drop`, `--security-opt`, `-u`, `--group-add` |
| `ulimits`, `sysctls`, `shm_size`, `pids_limit` | `--ulimit`, `--sysctl`, `--shm-size`, `--pids-limit` |
| `cpus`, `cpuset`, `cpu_shares`, `cpu_period`, `cpu_quota`, `cpu_rt_period`, `cpu_rt_runtime`, `cpu_count`, `cpu_percent` | The matching `--cpu*` flags. |
| `mem_limit`, `mem_reservation`, `memswap_limit`, `mem_swappiness`, `oom_kill_disable`, `oom_score_adj` | `--memory`, `--memory-reservation`, `--memory-swap`, `--memory-swappiness`, `--oom-kill-disable`, `--oom-score-adj` |
| `labels`, `label_file`, `annotations` | `--label`, `--label-file`, `--annotation` |
| `working_dir`, `init`, `tty`, `stdin_open`, `stop_signal` | `-w`, `--init`, `--tty`, `--interactive`, `--stop-signal` |
| `runtime`, `platform`, `isolation`, `cgroup_parent`, `storage_opt`, `pull_policy` | `--runtime`, `--platform`, `--isolation`, `--cgroup-parent`, `--storage-opt`, `--pull` |

`ulimits` accepts both compose forms — `rtprio: 99` becomes `--ulimit rtprio=99`,
and `nofile: {soft: 1024, hard: 4096}` becomes `--ulimit nofile=1024:4096`.

**Keys sheppy ignores, with a warning** naming the reason: `restart`,
`depends_on`, `healthcheck`, `stop_grace_period`, `post_start`, `pre_stop`
(sheppy owns lifecycle); `build` (sheppy runs images, it doesn't build them);
`container_name`, `scale`, `profiles`, `extends`; `networks`, `links`,
`external_links`; `configs`, `secrets`; `develop`; `logging`, `attach`; and
`blkio_config`.

**Any other key is a validation error**, with a `did you mean` suggestion —
`ulimit: 99` is rejected rather than silently dropped. For an inline
`container` the error fails manifest validation; for a `compose` reference it
surfaces as a warning when the node launches.


## Things that surprise people

- **`privileged: true` does not raise rlimits.** Capabilities and rlimits are
  separate mechanisms: a privileged container still gets `RLIMIT_RTPRIO` of 0,
  so `sched_setscheduler(SCHED_FIFO, …)` fails with `EPERM` no matter which
  capabilities it holds. A real-time node needs `cap_add: [SYS_NICE]` *and*
  `ulimits: {rtprio: 99, memlock: -1}`. Both are necessary and neither is
  sufficient — the host also has to be RT-tuned (`isolcpus`, `nohz_full`,
  `rcu_nocbs`, CPU affinity), which the container contract cannot express. A
  successful `ulimits` declaration does not mean you have real-time.
- **`machines[].user` is required, not optional.** The loader errors if it's
  missing or empty, same as `name` and `host`.
- **`select:` accepts exactly one value: `single`.** It reads like a choice
  of selection strategies; it isn't one. Anything else is a validation
  error.
- **`params` on a `process` alternative are ignored**, with a warning at
  load time — `process` runs `command` verbatim and has nowhere to splice
  parameters in.
- **`publishes`/`subscribes` are documentation only.** sheppy stores and
  displays them but never checks them against the live ROS graph — nothing
  flags a starved subscription today.
- **`machine:` does not launch remotely.** It selects that machine's
  `ros_setup` to source before the command and is shown in the TUI's host
  column and detail panel — but `sheppyd` itself always runs locally, and
  the `docker` launcher doesn't even read `alt.machine`, so container
  alternatives get no `ros_setup` sourcing at all.
