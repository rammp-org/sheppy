# CLI reference

The `sheppy` command has two faces. Given a manifest path (or nothing), it
opens [the TUI](/tui); given a **verb**, it runs headless — the verbs never
import Textual, so they work on a machine with no display.

```bash
sheppy [MANIFEST]          # open the TUI (MANIFEST defaults to ./system.yaml)
sheppy <verb> [...]        # headless: up, down, status, logs, woof, daemon
```

Everything below is verified against `sheppy/cli.py`.

## Verbs

### `sheppy up <profile> [--manifest PATH]`

Resolve the profile against the manifest (`--manifest` defaults to
`system.yaml`), print the plan (`start` / `stop` / `restart` per node),
converge the running system to it, wait until every node settles (30 s
timeout), and print the final state per node.

- **Idempotent:** nodes already running the right command are left untouched;
  missing ones are started; ones running a different command are replaced.
  Running it twice in a row prints `already converged` the second time.
- **Orphans are untouched:** processes the daemon supervises that aren't in
  the manifest are ignored by the diff.
- **Auto-spawns the daemon** if it isn't running — the only verb that does.
- **Exit code:** non-zero if the manifest or profile fails to load, if any
  node ends up `crashed`, or on settle timeout. Manifest/profile issues that
  are recoverable print as `warning:` on stderr and don't block the launch.

### `sheppy status`

One line per supervised node: state, alternative id, pid, and uptime (or exit
code for a crashed node). Prints `(nothing supervised)` when the table is empty and
`sheppyd: not running` when there's no daemon — both exit 0.

### `sheppy logs <node> [-n N]`

Print the last `N` (default 50) log lines for a node. Exits 1 with an error
on stderr if the node is unknown (or the daemon isn't running).

### `sheppy woof <node>` 🐕

Restart a node. Exits 1 if the node is unknown or the daemon isn't running.

### `sheppy down`

Stop every supervised node (printing `stopped <node>` for each), then stop
the daemon itself. Exits 0 even if the daemon wasn't running.

### `sheppy daemon status` / `sheppy daemon stop`

Report whether `sheppyd` is running and how many nodes it supervises, or stop
the daemon **while leaving the children running** — a restarted daemon
[re-adopts them](/guides/sheppyd#survivability-and-re-adoption). This is the
difference from `sheppy down`, which stops the nodes too.

## Exit codes at a glance

| Situation | Code |
|-----------|------|
| Success | 0 |
| Daemon not running — `down`, `status`, `daemon` | 0 |
| Daemon not running — `logs`, `woof` | 1 |
| Unknown node (`logs`, `woof`) | 1 |
| `up`: manifest/profile failed to load, a node crashed, or settle timeout | 1 |

## `sheppyd`

You normally never run the daemon yourself — the first launch action spawns
it. Running `sheppyd` by hand starts it in the foreground: it takes the
single-instance lock, re-adopts surviving children, and serves on the local
socket until SIGTERM/SIGINT. See the
[sheppyd guide](/guides/sheppyd) for its lifecycle, configuration, and
protocol.

## Environment

| Variable | Effect |
|----------|--------|
| `SHEPPY_HOME` | Pin logs, state, config, and the socket under this directory instead of `~/.sheppy` (the socket otherwise prefers `$XDG_RUNTIME_DIR`). Useful for test isolation. |
| `COLORTERM=truecolor` | Required for the TUI's full palette over SSH — see [colors washed out over SSH?](/tui#colors-washed-out-over-ssh) |
